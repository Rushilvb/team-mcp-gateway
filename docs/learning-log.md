## Phase 0: Scaffold

### What was built
- Repo layout: `charts/` (two Helm charts, filled in later), `services/` (five services), `scripts/`, `docs/`.
- `k3d/cluster.yaml`: a 2-node local Kubernetes cluster (1 server + 1 agent) running k3s `v1.36.5+k3s1`, with host ports 80/443 mapped to the cluster's ingress.
- `Makefile`: `cluster-up` (idempotent), `status`, `teardown`, and stubs for later targets.
- `.gitignore` (secrets, PDFs, build output) and `.gitattributes` (forces LF line endings so scripts run in WSL).

### Key concepts
- **k3s**: a lightweight but fully conformant Kubernetes distribution, shipped as a single binary. It bundles Traefik (ingress controller), a local-path storage provisioner, a service load balancer (ServiceLB/klipper), and a NetworkPolicy controller.
- **k3d**: runs k3s *inside Docker containers*. Each "node" is a container. That gives a disposable local cluster that runs the same k3s as the VPS.
- **Nodes, server vs agent**: a node is a machine (here a container) that runs pods. The *server* runs the control plane (API server, scheduler, controller manager, datastore) and can also run pods. *Agents* only run pods.
- **Ingress vs ingress controller**: an Ingress is just a routing rule ("host shop.localtest.me → service wordpress"). The *ingress controller* (Traefik) is the actual reverse proxy that reads those rules and forwards traffic. Without a controller, Ingress objects do nothing.
- **Port mapping**: k3d puts an nginx loadbalancer container in front of the nodes. `80:80@loadbalancer` publishes host port 80 on it, and it forwards to Traefik's LoadBalancer Service inside the cluster.
- **localtest.me**: a public DNS wildcard where every subdomain resolves to 127.0.0.1, so hostname-based Ingress routing works locally without editing hosts files.

### Likely interview questions
1. **Why k3d instead of Kind or Minikube?**
   k3d runs k3s, the same distribution I deploy on the VPS. Traefik, local-path storage and the NetworkPolicy enforcement behave the same in both places, so "works locally" means "works in prod" with only values-file changes. Kind would need an ingress controller and a CNI with NetworkPolicy support added by hand.
2. **When you open http://shop.localtest.me, what happens step by step?**
   DNS resolves it to 127.0.0.1. The browser connects to port 80 on the host, which Docker publishes on the k3d loadbalancer container. That container forwards to Traefik inside the cluster. Traefik matches the Host header against Ingress rules and proxies to the matching Service, which load-balances to a ready pod. Today there's no rule yet, so Traefik returns 404, which proves everything up to Traefik works.
3. **Why pin the k3s version?**
   For reproducibility. Kubernetes minor versions change APIs and defaults. Pinning the image locally and setting `INSTALL_K3S_VERSION` on the VPS to the same version removes "different cluster version" as a source of bugs.

## Phase 1: Store (WordPress + WooCommerce + MariaDB)

### What was built
- `charts/store`, our own Helm chart using only official images (`mariadb`, `wordpress`, `wordpress:cli`). Release `store` in namespace `store`.
- **MariaDB**: StatefulSet (1 replica) + headless Service + a PVC per pod from `volumeClaimTemplates`.
- **WordPress**: Deployment (1 replica, `Recreate` strategy) + ClusterIP Service + PVC for `wp-content` + Ingress for `shop.localtest.me`.
- **Secrets** (all generated by Helm, kept across upgrades): DB passwords, WP admin password, WP auth salts, WooCommerce REST API consumer key/secret.
- **Bootstrap Job** (Helm `post-install,post-upgrade` hook): installs WordPress core and WooCommerce 11.2.1; sets site URL, pretty permalinks, Asia/Kolkata, INR, COD; creates 3 sample products, a `shop_manager` user `woo-mcp`, and its REST API key. Every step checks state first, so re-running changes nothing.
- `make deploy-local`, `make store-admin`, `make store-logs`.

### Key concepts
- **Deployment vs StatefulSet**: a Deployment's pods are interchangeable (random names, any can be replaced). A StatefulSet gives each pod a stable name (`store-mariadb-0`) and its *own* PVC that it gets back after every restart. That's what a database needs.
- **PVC / PV / StorageClass**: a PersistentVolumeClaim is a request ("2Gi, ReadWriteOnce"). A StorageClass's provisioner fulfils it by creating a PersistentVolume. On k3s that's `local-path`: a directory on the node's disk, so the PV is pinned to that node. `ReadWriteOnce` means "mountable by one *node*", not one pod.
- **Headless Service** (`clusterIP: None`): DNS returns the pod IPs directly instead of a virtual IP. StatefulSets require one for stable per-pod DNS names.
- **Probes**: *startup* (don't judge liveness until first boot finishes; MariaDB init is slow), *readiness* (should this pod receive traffic now? WordPress checks `wp-login.php`, which needs PHP + DB), *liveness* (is the process stuck, so a restart helps? We only check that Apache answers, because restarting WordPress doesn't fix a down DB).
- **Helm `lookup` for secrets**: templates generate random passwords. Without `lookup`, every `helm upgrade` would generate *new* ones and lock WordPress out of a DB initialised with the old ones. The helper prefers an explicit value, else the live Secret's value, else a new random one. `helm.sh/resource-policy: keep` stops `helm uninstall` from deleting Secrets whose data volume survives.
- **Helm hooks**: resources annotated `helm.sh/hook` are run at a lifecycle point instead of being part of the release. `post-install,post-upgrade` + `--wait` means the Job runs after MariaDB and WordPress are Ready. `hook-delete-policy: before-hook-creation` keeps the last run (and its logs) until the next one.
- **Why the Job has an initContainer**: `wordpress:cli` has no WordPress core, and the live pod's core isn't on a volume. The initContainer copies core from the same `wordpress` image into an `emptyDir`, and the real `wp-content` PVC is mounted on top. wp-cli then edits the real DB and real plugin directory.
- **Non-root**: MariaDB runs as uid 999, WordPress and the Job as uid 33 (`www-data`). Apache must bind port 80, which normally needs root. The pod sets the namespaced sysctl `net.ipv4.ip_unprivileged_port_start=0`, which Kubernetes treats as "safe" (no cluster config needed).
- **Bug we hit: volume ownership.** First deploy, WordPress crash-looped with `tar: ./wp-content: Cannot change mode ... Operation not permitted`. k3s `local-path` volumes are plain host directories owned by root, and `fsGroup` (which normally makes Kubernetes chown the volume to the pod's group) is *not applied* to that volume type. So the non-root entrypoint couldn't chmod its own mount. Fix: a `volume-permissions` initContainer that runs as root but with every capability dropped except `CHOWN`, and only runs `chown 33:33` on the mount point. It's a values toggle (`volumePermissions.enabled`) because storage that honours `fsGroup` doesn't need it. MariaDB didn't hit this because its entrypoint never chmods the data dir (local-path creates it 0777).
- **WooCommerce API key storage**: WooCommerce stores `HMAC-SHA256(consumer_key, "wc-api")`, never the plain key. The consumer *secret* is stored plain because WooCommerce needs it to verify OAuth 1.0a signatures. We generate both in a Kubernetes Secret and insert the row ourselves (`files/api-key.php`, mirroring `WC_Auth::create_keys()`). So the Job never needs RBAC to write Secrets.

### Likely interview questions
1. **Delete the WordPress pod. Why does nothing get lost?**
   Nothing important lives in the pod. Orders, products and settings are in MariaDB, whose files are on its PVC. Plugins and uploads are on the `wp-content` PVC. WordPress core comes from the image, and the salts come from a Secret, so even login cookies stay valid. The Deployment creates a new pod that mounts the same PVC. Same for `store-mariadb-0`: the StatefulSet recreates it with the same name and reattaches `data-store-mariadb-0`.
2. **Why does running `helm upgrade` twice not break or duplicate anything?**
   Secrets: `lookup` returns the existing values, so passwords never change. Bootstrap: every step checks first (`wp core is-installed`, plugin version, product by SKU, user exists, API key hash already present), and settings are plain "set to X" operations. No pod-restart annotations change either, so pods aren't rolled.
3. **Why generate the API key in Helm instead of letting WooCommerce create one?**
   If WooCommerce generated it, the key would only exist inside WordPress, and the Job would need Kubernetes RBAC to write it into a Secret for the MCP server. Generating it in Helm means the Secret is the source of truth and the Job only needs DB access it already has. The trade-off is that we must match WooCommerce's storage format exactly (HMAC hash, truncated key), which we copy from `WC_Auth::create_keys()`.

## Phase 2: WooCommerce MCP server

### What was built
- `services/woo-mcp`: Python MCP server (official SDK `mcp==2.2.0`, class `MCPServer`) with 6 tools: `get_info`, `list_products`, `create_product`, `list_orders` (incl. `date="today"` in Asia/Kolkata), `get_order`, `update_order_status`. Served over Streamable HTTP at `/mcp` (stateless, JSON responses) by uvicorn, plus `/healthz`.
- `woo_mcp/oauth.py`: a hand-written OAuth 1.0a signer matching WooCommerce's verifier. `woo_mcp/woo_client.py`: thin httpx client (signing, Host header, no redirects, timeouts, clean errors).
- 23 unit tests (REST mocked with `respx`; tools called through a real in-memory MCP client). Run with `make test` inside a Docker build stage.
- `charts/platform` (namespace `platform`): woo-mcp Deployment (non-root, read-only root FS, no service-account token), ClusterIP Service, **no Ingress**, a Secret copied from the store via `lookup`, and a NetworkPolicy.
- Makefile: `test`, `build`, `load-images`, `lint`; `deploy-local` now installs both charts. Image tags are a hash of the source.

### Key concepts
- **MCP in one paragraph**: a JSON-RPC protocol between a *client* (Claude Code, Inspector, later our gateway) and a *server* that offers tools. The client calls `initialize`, then `tools/list` (names + descriptions + JSON Schemas for arguments), then `tools/call`. The tool's result is content the model reads; failures come back as results with `isError: true`, so the model can see and react to them.
- **Streamable HTTP transport**: every MCP message is an HTTP POST to one endpoint (`/mcp`). The server may answer with JSON or upgrade to an SSE stream. We run **stateless** (no `Mcp-Session-Id` kept server-side), so restarts or extra replicas lose nothing. **JSON responses** make it plain request/response.
- **Schemas from type hints**: `Annotated[int, Field(ge=1, le=100)]` becomes `{"type":"integer","minimum":1,"maximum":100}` in `tools/list`. The SDK validates arguments *before* our code runs (our tests prove bad input never reaches the store).
- **DNS-rebinding protection**: the SDK checks the `Host` header. Its default only allows localhost, so in-cluster callers (`woo-mcp.platform.svc...`) would be rejected. We pass the allowed hosts explicitly.
- **OAuth 1.0a (one-legged)**: instead of sending the secret, sign each request: HMAC-SHA256 over method + URL + sorted query params, keyed with the secret. A nonce and timestamp stop replays. WooCommerce requires it over plain HTTP (it refuses Basic auth without TLS). Quirk: WooCommerce signs its *home URL*, so we sign `http://shop.localtest.me/...` while sending to the in-cluster Service with `Host: shop.localtest.me`.
- **Cross-namespace Secrets**: a pod can only use Secrets from its own namespace. Helm `lookup` reads `store/store-woo-api` at deploy time and creates `platform/woo-mcp-store-api`. It fails with a clear message if the store isn't deployed. A checksum annotation restarts woo-mcp if the copied key changes.
- **NetworkPolicy**: once a policy selects a pod, all traffic not explicitly allowed is denied. woo-mcp: ingress only from pods labelled `gateway`; egress only to WordPress pods in `store` on port 80, plus DNS. DNS must be allowed explicitly, or even the store's name won't resolve. k3s *rejects* blocked connections, so they show "connection refused" rather than timing out. `kubectl port-forward` isn't affected: the kubelet connects inside the pod's own network namespace.
- **Image tags from content hashes**: tag = hash of the service's files. Same code → same tag (Helm does nothing); changed code → new tag (Helm rolls the pod). No `latest`, no "did it pick up my change?" confusion.

### Likely interview questions
1. **Why is the MCP server internal-only, and how do you prove it?**
   It holds a store credential that can create products and change orders. The only thing that should use it is the gateway, which adds auth, per-user attribution and audit. So: ClusterIP only, no Ingress, and a NetworkPolicy allowing ingress only from gateway pods. Proof, with controls: a random pod in `platform` is refused, while an identical pod labelled `app.kubernetes.io/name=gateway` gets `ok`. From inside woo-mcp, the store answers 200 while the internet and MariaDB are refused.
2. **Why did you write the OAuth signing yourself instead of using a library?**
   The tricky part isn't the HMAC, it's WooCommerce's quirks: it rebuilds the URL from its home URL, only signs query params, and has a specific encoding and key format. ~30 lines that mirror its PHP verifier are easier to explain and debug than configuring a general library around those quirks. And it's verified: the test's golden signature was accepted by WooCommerce's own `check_oauth_signature()` running in the store pod, and a wrong one was rejected.
3. **What happens when the store is down?**
   woo-mcp stays up and Ready: `/healthz` deliberately doesn't check the store, because restarting woo-mcp can't fix WordPress. Each tool call fails fast (10s timeout) with an MCP tool error, `store unreachable: timed out after 10s`, so the model or user sees a clear reason. The gateway (Phase 4) will keep listing woo-mcp's tools from its cache and report the call error.

## Phase 3: Notes + FX MCP servers (and Postgres)

### What was built
- **Postgres 18** in the platform chart: StatefulSet (non-root uid 999) + PVC + headless Service. A one-time init script creates two databases with separate owner roles: `notes` and `gateway` (the latter for Phase 4).
- **notes-mcp**: `add_note`, `list_notes`, `search_notes`, `get_info` over asyncpg. Requires `Authorization: Bearer <token>`.
- **fx-mcp**: `convert_currency`, `list_rates` from a ConfigMap of reference rates (Decimal maths, file re-read per call). Requires `X-API-Key`.
- A shared ~40-line pure-ASGI auth middleware (constant-time compare, 401 + JSON, `/healthz` open).
- Secrets generated by Helm and kept across upgrades: three Postgres passwords (one Secret per consumer), the notes token, the fx key.
- NetworkPolicies: notes (gateway in → Postgres out), fx (gateway in → **nothing** out), Postgres (notes + gateway in → nothing out).
- `make test` now runs all suites in containers; notes runs against a real throwaway Postgres. Also new: `make mcp-tokens`.

### Key concepts
- **Why two credential types?** The gateway must support `bearer` (`Authorization: Bearer x`) and `header` (any header name, e.g. `X-API-Key: x`). Each upstream demonstrates one, so Phase 4 can prove both injection paths.
- **Constant-time comparison**: `a == b` stops at the first differing byte, so response time leaks how much of a guess was right. `hmac.compare_digest` always takes the same time.
- **Pure ASGI middleware**: an ASGI app is just `async def app(scope, receive, send)`. Our wrapper looks at `scope["headers"]` and either calls the inner app or sends a 401 itself. Starlette's `BaseHTTPMiddleware` buffers and wraps the response, which is known to break streaming (MCP may stream).
- **Postgres init scripts run once**: the image runs `/docker-entrypoint-initdb.d/*` only when the data directory is empty. So all databases are created up front, and adding one later needs a manual step or a migration Job.
- **Least privilege in the database**: each service has its own role that owns only its database, with `REVOKE ALL ... FROM PUBLIC`. Verified: the `notes` role gets `permission denied for database "gateway"`. Each pod only receives *its* password Secret.
- **Lifespan once per process**: in MCP SDK 2.x the Streamable HTTP session manager enters the server lifespan once, so the DB pool is opened once (not per request) and closed on shutdown. Uvicorn finishes startup before it listens, so the pod isn't Ready until the DB is.
- **Mounted ConfigMaps update in place** (not env vars, which are fixed at pod start). That's why fx-mcp reads the file per call: new rates apply without a restart.
- **Default-deny egress**: `egress: []` with `policyTypes: [Egress]` blocks everything, even DNS. That's right for fx-mcp, which never needs the network. A compromised fx-mcp can't phone home.
- **Testing against a real DB**: a Docker *build* step can't reach other containers, so test stages became `CMD pytest`. `make test` starts `postgres:18.4` on a private Docker network and passes `TEST_DATABASE_URL`.

### Likely interview questions
1. **How do the upstream servers authenticate the gateway, and where do those secrets live?**
   Static credentials: notes wants `Authorization: Bearer <token>`, fx wants `X-API-Key: <key>`. Helm generates them into Kubernetes Secrets (kept across upgrades), and the servers read them from env. In Phase 4 the gateway stores them encrypted (Fernet) in its DB and injects them per upstream call. Team members never see them, and member tokens are never forwarded. Each server compares in constant time and has a NetworkPolicy, so even with the token you can't reach it except from a gateway pod.
2. **Why does notes-mcp get its own database user instead of the Postgres superuser?**
   Blast radius. If notes-mcp were compromised, the attacker gets a role that owns only the `notes` database. It can't connect to `gateway` (users, API-key hashes, encrypted upstream credentials) and can't create roles. Combined with one Secret per consumer, no pod ever holds a password it doesn't need.
3. **What happens to notes when Postgres restarts?**
   Data is on the PVC, so it survives (verified: deleted `postgres-0`, the note was still there). While Postgres is down, notes tool calls return `notes database unavailable`. After it comes back, the asyncpg pool replaces dead connections and calls work again without restarting notes-mcp. If notes-mcp itself starts while Postgres is down, it waits up to 60s, then exits, and Kubernetes restarts it.

## Phase 4: Gateway core

### What was built
- `services/gateway`: FastAPI app hosting one MCP endpoint, `/mcp`, built on the MCP SDK's **low-level** `Server` so the tool list is computed per request.
- **Auth**: a pure-ASGI wrapper. `Authorization: Bearer urk_…` is SHA-256-hashed and looked up on every request. Revoked keys get 401, plus a `denied` audit row naming the user and tool.
- **Registry**:
  - One HTTP pool per upstream, carrying that upstream's credential. Created lazily, rebuilt after failures, SSRF-checked on every (re)build.
  - A concurrent health loop every 15s, with a tool cache and status (`connected` / `unreachable` / `disabled`).
  - Tool calls with a 15s timeout.
- **Naming** `<slug>__<tool>`; `list_changed` notifications via the SDK's subscription bus.
- **Postgres schema** via Alembic (`users`, `api_keys`, `upstream_servers`, `audit_log`). An initContainer runs the migration.
- **Bootstrap** from Secrets and values: an admin user, plus woo, notes and fx with their credentials **encrypted with Fernet**.
- **SSRF guard**, an admin **CLI** (`make gateway-user/key/revoke/upstreams/audit`), and an **Ingress** at `app.localtest.me/mcp`.
- **NetworkPolicy**: in only from Traefik. Out only to Postgres, our MCP servers, DNS, and public internet on 80/443 (private and link-local ranges excluded).
- **Tests**: 50, against real Postgres and HTTP, with fake upstreams (no-auth, bearer, slow header, dead) covering every CLAUDE.md requirement.

### Key concepts
- **Aggregation = MCP client + MCP server in one process.** Towards clients the gateway is an MCP *server*; towards woo, notes and fx it is an MCP *client*. `tools/list` merges what it learned as a client; `tools/call` forwards as a client.
- **Low-level vs high-level SDK**: `MCPServer` (`@tool` decorators) suits a fixed set of tools defined in code. The gateway's tools change at runtime, so it registers `on_list_tools`/`on_call_tool` handlers on the low-level `Server` and builds `Tool` objects itself.
- **Knowing the user inside an MCP handler**: our auth wrapper stores the `Principal` in the ASGI `scope["state"]`. The SDK exposes the HTTP request as `ctx.request`, so the handler reads `ctx.request.state.principal`. (Verified for both protocol eras before building on it.)
- **Per-user identity vs shared upstream credential**: members authenticate *to the gateway*. The gateway authenticates *to upstreams* with one shared credential per upstream, which members never see. So upstreams can't tell members apart, and attribution comes from the gateway's audit log.
- **Cache-based listing**: `tools/list` reads a cache filled by the health loop. Listing never waits on an upstream, so a dead upstream can't slow it or break it. The cost is staleness of up to one interval, which is why `list_changed` exists.
- **Timeouts with anyio**: `with anyio.fail_after(15): await call()` cancels the call if it overruns. We turn that into a clear tool error and audit it as `timeout`. Concurrency for health checks uses an anyio task group, so each upstream is checked in parallel with its own timeout.
- **The 2026-07-28 MCP protocol**: requests are self-contained (no initialize handshake or session), which is why "one long-lived session per upstream" became "one HTTP pool per upstream, stateless calls over it". Server→client events need an explicit `subscriptions/listen` stream, so older clients just re-list.
- **API key vs password hashing**: a 256-bit random key can't be guessed or dictionary-attacked, so a fast SHA-256 is enough (and keeps per-request lookup cheap). Passwords are low-entropy, so they need slow, salted argon2id.
- **Fernet**: symmetric authenticated encryption (AES-128-CBC + HMAC-SHA256). The key lives in a Kubernetes Secret, not in the DB, so a DB dump alone doesn't expose upstream credentials.
- **SSRF**: if admins can make the server fetch URLs, an attacker-admin (or a typo) could point it at `169.254.169.254`, `localhost`, or internal services. We validate the scheme and host, allow cluster names only from an allowlist, and check *every resolved IP*. We re-check on each reconnect (DNS rebinding) and back it with a NetworkPolicy.
- **Alembic**: versioned schema changes. The initContainer runs `upgrade head` before the app starts, and `alembic check` in tests fails if the models drift from the migrations. A naming convention gives constraints stable names, so future migrations can reference them.

### Likely interview questions
1. **Walk me through a `tools/call` for `notes__add_note`.**
   Traefik routes `app.localtest.me/mcp` to the gateway. `McpAuth` hashes the bearer key, finds an active key and user, and stores the Principal. The SDK parses JSON-RPC and calls our `call_tool`. We split `notes__add_note` into `notes` + `add_note` and check notes is enabled. We send `add_note` over notes' HTTP pool, which carries `Authorization: Bearer <notes token>` (decrypted from the DB), never the member's key, with a 15s timeout. We pass the result back unchanged and write an audit row: user, channel `api`, `notes`, tool, start time, duration, outcome.
2. **What happens when an upstream dies mid-demo?**
   Within one health interval its check fails (connection refused or timeout). Status becomes `unreachable` with the error stored, and its tools drop out of the cache. So `tools/list` from any client no longer shows them, and modern clients get `list_changed`. Other upstreams are unaffected because checks run concurrently, each with its own timeout. A direct call to its tool returns a clear `upstream 'fx' is unreachable: …` error and is audited. When it comes back, the next check restores it. (Verified by scaling fx-mcp to 0 and back.)
3. **How do you guarantee members never see upstream credentials, and upstreams never see member keys?**
   Credentials are Fernet-encrypted in the DB, decrypted only in memory into the upstream's own HTTP pool headers, and never serialized into any response (a future REST API returns only "credential set: yes/no"). Error messages are scrubbed of the credential as defense in depth. Member keys are consumed by `McpAuth` and never copied onto upstream requests, because upstream pools are built from upstream config only. Tests assert both directions: fake upstreams record every header they receive (their own credential, never `urk_…`), and every response and error body is scanned for the secrets.

### Phase 4 addendum (review fixes)
- **Legacy upstreams.** Most third-party MCP servers still speak the pre-2026 protocol (`initialize` handshake + `Mcp-Session-Id`).
  - The client's `auto` mode probes `server/discover`, and a legacy server rejects it, so the client falls back to the handshake.
  - We remember the era per upstream, so we don't pay a failed probe on every call.
  - Tested against a session-based fake that rejects modern requests like an old server; the test asserts exactly one probe.
- **Bootstrap seeds only an empty registry.** Before, each default was re-added "if missing", so a server an admin deliberately removed would reappear on the next restart. Now the DB is the source of truth after the first start (tested by removing and renaming, then restarting).
- **Loopback for the chat agent.** `127.0.0.1:*` and `localhost:*` are accepted Host headers.
  - The Phase 6 agent calls `http://127.0.0.1:8000/mcp` inside the same pod.
  - Calling itself through its Service name is refused by its own NetworkPolicy (ingress only from Traefik). That's a good example of policies applying even to a pod talking to itself via a Service.
- **Recorded for Phase 5.** Admin enable/disable/edit/remove must call `registry.refresh()` right after committing, so changes apply immediately rather than on the next health tick.

**Likely question: why remember the protocol era instead of probing every time?** With per-call clients, `auto` mode against a legacy server costs a rejected `server/discover` round trip on *every* call and health check, which is wasted latency and log noise on the upstream. We probe once, cache the result on the connection, and clear it on reset, so an upgraded server gets re-detected.

## Phase 5: REST API, auth/roles, dashboard

### What was built
- **REST API** in the gateway (`gateway/api/`, FastAPI routers):
  - login/logout/me, invite links, members (invite, role, enable/disable), API keys (own; admins: anyone's), upstream servers (CRUD + test), audit (filters + pagination).
  - Alembic migration `0002` adds `user_sessions` and invite columns.
- **Dashboard** (`services/dashboard`): React 19 + TypeScript 7 + Vite 8 + Pico CSS, served by non-root nginx with a strict CSP.
  - Pages: Login, Accept invite, Servers, Members, API keys (+ "Connect your MCP client"), Audit, Chat (placeholder).
- **Platform chart:**
  - Dashboard Deployment (read-only root FS, `emptyDir` for `/tmp`).
  - One `app` Ingress: `/mcp` and `/api` → gateway, `/` → dashboard.
  - Dashboard NetworkPolicy (in from Traefik only, no egress).
  - Gateway env `PUBLIC_URL` and `COOKIE_SECURE`.
- **Proof of server-side roles:** 22 new API tests (75 gateway tests total) and `make api-role-check` (curl through the real Ingress: 403 on every admin endpoint for a member).

### Key concepts
- **Sessions vs tokens**: a server-side session is a random ID in a cookie plus a DB row. Because the server looks it up every time, logout, disabling or a role change takes effect on the very next request. A signed stateless cookie (JWT style) can't be revoked before it expires without a denylist, which is just a session table again.
- **Cookie flags**:
  - `HttpOnly`: JavaScript can't read the cookie, so an XSS bug can't steal it.
  - `SameSite=Strict`: the browser doesn't attach it to requests started by other sites (the main CSRF defense).
  - `Secure`: only sent over HTTPS (on in prod).
- **CSRF**: another site makes your browser send a request with *your* cookie. Defenses here are `SameSite=Strict` plus an `Origin` check on every state-changing request (browsers always send `Origin` on POST/PATCH/DELETE). Non-browser clients (curl) don't send it, and they can't hold a victim's cookie anyway.
- **Same origin, no CORS**: the UI and the API live on one host (`app.localtest.me`), split by path at the Ingress. The browser treats them as one origin, so there's no CORS config, the cookie just works, and the CSP can say `connect-src 'self'`.
- **AuthN vs AuthZ in FastAPI**: dependencies run before a route. `current_user` (who are you? 401 if nobody) and `require_admin` (may you? 403 if not) are declared per route, so a route can't forget authorization: its signature shows it. The UI hiding buttons is convenience only.
- **Enumeration-resistant errors**:
  - Same message and similar timing for a wrong password vs an unknown email (we still run argon2 against a dummy hash).
  - 404, not 403, for another user's key ID.
  - Login rate limit: 5 failures per 15 minutes.
- **Invite links**: a bearer secret in a URL, so treat it like a password. It's random, stored only as a hash, expires, and is single-use. Showing it once to the admin replaces email delivery.
- **Write-only secrets in an API**: responses never contain upstream credentials (`credential_set` instead). PATCH distinguishes "field omitted" (keep) from `null` (clear) with Pydantic's `model_fields_set`.
- **SPA + nginx**: nginx returns `index.html` for unknown paths and React Router picks the page. Hashed asset names (`index-CKC3tAsL.js`) can be cached for a year because a new build means a new name.
- **CSP**: `default-src 'self'` means the browser refuses inline scripts and anything from other origins, so injected `<script>` tags don't execute. We avoided inline styles too, so `style-src 'self'` holds.
- **Bug the tests caught**: after an admin change, the API returned the *old* status. The registry wrote the new status through its own DB session, but the request's session (with `expire_on_commit=False`) still had the row cached. Fix: `session.expire_all()` before re-reading.

### Likely interview questions
1. **How do you make sure a member can't do admin things?**
   Every admin route depends on `require_admin`, which re-reads the user from the database for each request via their session. It's verified twice: `tests/test_api.py` calls every admin endpoint as a member and as an anonymous user (403/401), and `make api-role-check` does the same with curl through the real Ingress against the deployed system. Members' audit queries are rewritten server-side to `user_id = self`, whatever they ask for. The dashboard hiding buttons is just UX.
2. **Why server-side sessions instead of a JWT?**
   Immediate revocation and less to get wrong. Logout deletes the row, and disabling a user or demoting an admin applies on their next click. A JWT stays valid until expiry unless you add a denylist, which is a DB lookup per request anyway. With one gateway replica and Postgres already in place, a sessions table is the simplest correct design. The token is stored hashed, like API keys, so a DB leak doesn't hand out live sessions.
3. **Walk me through what happens when an admin disables the fx server in the dashboard.**
   `Servers.tsx` calls `api.updateServer("fx", {enabled:false})`, which sends `PATCH /api/servers/fx` with the session cookie. Traefik routes `/api` to the gateway, where the Origin check runs and `require_admin` passes. The route sets `enabled=false`, commits, then awaits `registry.refresh()` (under a lock shared with the health loop). The refresh drops fx's pool and tool cache and publishes `list_changed`. The response returns the new state, so every MCP client's next `tools/list` lacks `fx__*` (measured 0.06s after the click) and a direct call returns `upstream 'fx' is disabled` (audited as `denied`).

### Phase 5 addendum (review)
- **Admin-issued keys**: `POST /api/users/{id}/keys` plus an "Issue a key" button under a member's keys.
  - The key belongs to the member, so their calls are audited under their name, and it's shown once to the admin to hand over.
  - Refused for invited or disabled users, because their keys wouldn't work.
  - Tested, live-checked, and added to `api-role-check`: a member calling it for themselves gets 403.
- **CSP and inline styles**: `style-src 'self' 'unsafe-inline'`, so inline styles can't break the UI. `script-src` stays strict.
  - Why allowing inline *styles* is fine: XSS is about running script, and CSS can't execute code. At worst, injected CSS could restyle the page, which matters little in an app that renders no third-party HTML.
- **Re-issue invite**: `POST /api/users/{id}/invite` replaces the hash, so the old link dies (now tested).

**Likely question: why let admins create keys for others; doesn't that break "show once, only the owner knows it"?** The key is still shown exactly once and stored only hashed. It's for onboarding (a teammate's CI job, or someone without dashboard access yet). Accountability is preserved: the key is owned by the member (audit attribution) and its default name records which admin issued it. The member can see and revoke it on their own keys page, and so can any admin.

## Phase 6: Chat agent

### What was built
- **`gateway/chat/`:**
  - `token.py`: short-lived HMAC chat tokens.
  - `llm.py`: the `LLMProvider` interface and `GeminiProvider` (`google-genai` 2.28.0).
  - `agent.py`: the tool loop and system prompt.
- **`POST /api/chat`** (stateless: the browser sends the visible conversation).
- `auth.py` accepts `urc_` chat tokens → `Principal(channel="chat")`.
- **Dashboard Chat page:** message list, suggested prompts, expandable tool-call chips.
- **Chart:** chat env, with `GEMINI_API_KEY` from an *optional* Secret.
- **Makefile:** `make llm-secret` (kubectl-created Secret) and `make chat-check`.
- **Tests:** 11 chat tests with a scripted fake LLM driving the real loop through the real gateway (88 gateway tests total).

### Key concepts
- **Tool calling** (function calling): we send the model the tool list (names, descriptions, JSON Schemas). The model either answers or replies "call X with these arguments". *We* execute the call and send the result back, and the model continues. The model never touches the network; it only proposes calls.
- **Why the agent calls our own `/mcp`** instead of the registry directly: one enforcement point. Auth, disabled upstreams, timeouts, credential injection and audit all apply identically to Claude Code and to chat, with nothing duplicated or bypassed. We call it over loopback (`127.0.0.1:8000`), because the gateway's NetworkPolicy only admits Traefik, so its own Service name would be refused.
- **Chat token**: the browser's session cookie must not be sent to `/mcp`, and the user may have no API key. So the gateway mints a 5-minute `urc_` token: user id + expiry, signed with HMAC-SHA256.
  - Verification is a constant-time signature check, an expiry check, then a DB check that the user is still active.
  - The signing key is random per process, since only this process mints and verifies.
- **Provider interface**: `step(system, history, tools) -> Turn`. Swapping Gemini for another LLM is one class. Tests swap in a scripted fake, so they're deterministic, free and offline, while still exercising the real loop, real gateway, real audit and real upstreams.
- **Prompt injection**: a tool result (e.g. a product description or a note written by someone else) can contain text like "ignore your instructions and…". Mitigations:
  - **System prompt:** it says tool output is *untrusted data, not instructions*.
  - **Tools:** the model can only call the user's own tools, through the gateway, with the user's own permissions.
  - **Visibility:** every call is audited and visible as a chip.
  - **Limits:** max 8 steps, a 90s budget, and truncated results.

  Prompts alone can't guarantee safety, which is why the hard limits live in code.
- **Gemini "thought signatures"**: Gemini 3 models attach signatures to their function-call turns and require them back on the next request. We store the model's raw message for the duration of one request and resend it unchanged instead of rebuilding it.
- **Secrets outside Helm**: values passed to Helm are stored in its release Secret (history). `kubectl create secret ... --dry-run=client -o yaml | kubectl apply -f -` creates or updates the Secret idempotently without that. The pod references it with `optional: true`, so the app degrades gracefully (503) without it.

### Likely interview questions
1. **How are chat tool calls attributed to the right user?**
   `POST /api/chat` knows the user from their session cookie. It mints a chat token containing that user's id, signed by the gateway, and the agent uses it as the Bearer credential for its MCP client to `127.0.0.1:8000/mcp`. `McpAuth` verifies the signature and expiry, re-reads the user (must be active), and sets `Principal(user, channel="chat")`. The same audit code that records Claude Code calls records these, so the audit row has the user's id and channel `chat`. Tested end to end with a scripted model.
2. **What stops the model from doing something it shouldn't?**
   - **Capabilities:** the model only proposes calls; our code executes them as the user, through the gateway. So it can't exceed the user's access, use disabled upstreams, reach anything that isn't an MCP tool, or see credentials (they never enter its context).
   - **Hard limits in code:** 8 steps, 90s, truncated results, one chat at a time per user.
   - **Prompt and visibility:** the system prompt treats tool output as untrusted, and every call is audited and shown to the user as a chip.

   The residual risk is the model being tricked into a *legitimate* action, like changing an order status. That's covered in the threat model (Phase 8).
3. **Why is the chat stateless on the server?**
   Less to secure and nothing to clean up: no conversation table, no retention policy for possibly sensitive text. The browser sends the visible conversation (text only) each turn, capped at 40 messages × 8,000 chars. What matters for accountability (the tool calls) is already in the audit log.

## Phase 7: Hardening + Definition-of-Done check

### What was built
- **Store NetworkPolicies** (there were none):
  - `default-deny-ingress`.
  - WordPress: from Traefik + woo-mcp; out to mariadb, DNS, internet.
  - MariaDB: from wordpress/bootstrap; no egress.
  - Bootstrap Job: no ingress; out to mariadb, DNS, internet.
- **Platform:** a `default-deny-ingress` backstop.
- **Pod Security Admission:** `make namespaces` creates the namespaces with labels before Helm. platform = `restricted`; store = `baseline` + warn/audit `restricted`.
- **Store pods:** seccomp RuntimeDefault, no service-account token, WordPress drops ALL capabilities.
- **Scripts:**
  - `netpol-check.sh`: 21 live connection checks.
  - `security-check.sh`: per-container security table + the API server's restricted dry run.
  - **`dod-check.sh` / `dod_check.py`:** the whole DoD, 24 checks, standard-library Python + kubectl.
- **`docs/hardening.md`:** the inventory, with deliberate exceptions.
- **A real bug the DoD run found:** provider errors inside the chat loop escaped as HTTP 500s, because they arrive wrapped in an `ExceptionGroup`. That left a dangling connection which swallowed the next admin request. Now:
  - Errors are unwrapped.
  - A Gemini rate limit becomes **429 + Retry-After**, after one automatic wait if the delay is short.
  - Four new tests cover it (92 gateway tests).

### Key concepts
- **Default-deny**: a NetworkPolicy with `podSelector: {}` and no ingress rules selects *every* pod and allows nothing in. Other policies then *add* allowed paths: policies are additive (a union), there's no "deny" rule. The backstop protects pods nobody wrote a policy for yet.
- **Policies are per direction, and both sides must allow.** woo-mcp → WordPress needs woo-mcp's *egress* rule (platform) **and** WordPress's *ingress* rule (store). Cross-namespace rules combine a `namespaceSelector` and a `podSelector` in **one** `from` entry (AND); two separate entries would mean OR.
- **Pod Security Admission (PSA)**: a built-in admission controller with three standards.
  - **privileged:** anything goes.
  - **baseline:** blocks known escalations: privileged pods, hostPath, host networking, extra capabilities beyond a safe set.
  - **restricted:** additionally requires non-root, seccomp, drop ALL and no privilege escalation.

  Modes: `enforce` (reject the pod), `warn` (warning to the client), `audit` (record in the audit log). A server-side dry run (`kubectl label --dry-run=server ... enforce=restricted`) asks "would the running pods pass?" without changing anything.
- **seccomp RuntimeDefault**: the container runtime's default syscall filter blocks rarely needed, dangerous syscalls (e.g. kernel module loading). It's a cheap reduction of the kernel attack surface, and `restricted` requires it.
- **`automountServiceAccountToken: false`**: by default every pod gets a Kubernetes API token mounted. None of our workloads talk to the API, so a compromised pod shouldn't get a credential for it.
- **Testing in production-like conditions finds what unit tests don't.** The scripted LLM never raised errors, so the ExceptionGroup bug only appeared against a real model with a real quota. The fix came with tests for the exact failure.

### Likely interview questions
1. **Show me that only the gateway can reach woo-mcp.** `make netpol-check`.
   - A throwaway busybox pod in `platform` can't open a TCP connection to `woo-mcp:8000` (or notes, fx, postgres): blocked.
   - An identical pod wearing the label `app.kubernetes.io/name=gateway` connects: proof that it's the policy, not something else.
   - The caveat to volunteer: policies trust labels, so in production RBAC must restrict who can create pods in `platform`.
2. **Why is the store namespace only `baseline`, not `restricted`?** WordPress runs as non-root uid 33, but k3s's local-path volumes are root-owned directories, and `fsGroup` doesn't apply to that volume type. One init container runs as root with every capability dropped except CHOWN, and only chowns the volume. `baseline` allows that; `restricted` doesn't. `warn/audit=restricted` keeps the exception visible (`make security-check` lists exactly that one container). With a CSI storage driver that honours `fsGroup`, you'd turn the init container off and enforce `restricted`.
3. **What does the DoD script actually prove, and what can't it?** It drives the real system through public interfaces:
   - a Store API checkout;
   - the REST API as admin and members;
   - the chat endpoint with the real LLM;
   - raw MCP JSON-RPC as an external client;
   - kubectl to kill a pod.

   It checks each DoD item's observable effect, including the audit trail per user and channel. It can't click through the UI or use Claude Code itself; those stay manual demo steps, but they call the same endpoints the script exercises.
