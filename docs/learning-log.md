## Phase 0: Scaffold

### What was built
- Repo layout: `charts/` (two Helm charts, filled in later), `services/` (five services), `scripts/`, `docs/`.
- `k3d/cluster.yaml`: a 2-node local Kubernetes cluster (1 server + 1 agent) running k3s `v1.36.5+k3s1`, with host ports 80/443 mapped to the cluster's ingress.
- `Makefile`: `cluster-up` (idempotent), `status`, `teardown`, and stubs for later targets.
- `.gitignore` (secrets, PDFs, build output) and `.gitattributes` (forces LF line endings so scripts run in WSL).

### Key concepts
- **k3s**: a lightweight but fully conformant Kubernetes distribution, shipped as a single binary. It bundles Traefik (ingress controller), a local-path storage provisioner, a service load balancer (ServiceLB/klipper), and a NetworkPolicy controller.
- **k3d**: runs k3s *inside Docker containers*. Each "node" is a container. That gives a disposable local cluster that runs the same k3s as the VPS.
- **Nodes, server vs agent**: a node is a machine (here a container) that runs pods. The *server* runs the control plane (API server, scheduler, controller manager, datastore) and can also run pods. *Agents* only run pods.
- **Ingress vs ingress controller**: an Ingress is just a routing rule ("host shop.localtest.me → service wordpress"). The *ingress controller* (Traefik) is the actual reverse proxy that reads those rules and forwards traffic. Without a controller, Ingress objects do nothing.
- **Port mapping**: k3d puts an nginx loadbalancer container in front of the nodes. `80:80@loadbalancer` publishes host port 80 on it, and it forwards to Traefik's LoadBalancer Service inside the cluster.
- **localtest.me**: a public DNS wildcard where every subdomain resolves to 127.0.0.1, so hostname-based Ingress routing works locally without editing hosts files.

### Likely interview questions
1. **Why k3d instead of Kind or Minikube?**
   k3d runs k3s, the same distribution I deploy on the VPS. Traefik, local-path storage and the NetworkPolicy enforcement behave the same in both places, so "works locally" means "works in prod" with only values-file changes. Kind would need an ingress controller and a CNI with NetworkPolicy support added by hand.
2. **When you open http://shop.localtest.me, what happens step by step?**
   DNS resolves it to 127.0.0.1. The browser connects to port 80 on the host, which Docker publishes on the k3d loadbalancer container. That container forwards to Traefik inside the cluster. Traefik matches the Host header against Ingress rules and proxies to the matching Service, which load-balances to a ready pod. Today there's no rule yet, so Traefik returns 404, which proves everything up to Traefik works.
3. **Why pin the k3s version?**
   For reproducibility. Kubernetes minor versions change APIs and defaults. Pinning the image locally and setting `INSTALL_K3S_VERSION` on the VPS to the same version removes "different cluster version" as a source of bugs.

## Phase 1: Store (WordPress + WooCommerce + MariaDB)

### What was built
- `charts/store`, our own Helm chart using only official images (`mariadb`, `wordpress`, `wordpress:cli`). Release `store` in namespace `store`.
- **MariaDB**: StatefulSet (1 replica) + headless Service + a PVC per pod from `volumeClaimTemplates`.
- **WordPress**: Deployment (1 replica, `Recreate` strategy) + ClusterIP Service + PVC for `wp-content` + Ingress for `shop.localtest.me`.
- **Secrets** (all generated by Helm, kept across upgrades): DB passwords, WP admin password, WP auth salts, WooCommerce REST API consumer key/secret.
- **Bootstrap Job** (Helm `post-install,post-upgrade` hook): installs WordPress core and WooCommerce 11.2.1; sets site URL, pretty permalinks, Asia/Kolkata, INR, COD; creates 3 sample products, a `shop_manager` user `woo-mcp`, and its REST API key. Every step checks state first, so re-running changes nothing.
- `make deploy-local`, `make store-admin`, `make store-logs`.

### Key concepts
- **Deployment vs StatefulSet**: a Deployment's pods are interchangeable (random names, any can be replaced). A StatefulSet gives each pod a stable name (`store-mariadb-0`) and its *own* PVC that it gets back after every restart. That's what a database needs.
- **PVC / PV / StorageClass**: a PersistentVolumeClaim is a request ("2Gi, ReadWriteOnce"). A StorageClass's provisioner fulfils it by creating a PersistentVolume. On k3s that's `local-path`: a directory on the node's disk, so the PV is pinned to that node. `ReadWriteOnce` means "mountable by one *node*", not one pod.
- **Headless Service** (`clusterIP: None`): DNS returns the pod IPs directly instead of a virtual IP. StatefulSets require one for stable per-pod DNS names.
- **Probes**: *startup* (don't judge liveness until first boot finishes; MariaDB init is slow), *readiness* (should this pod receive traffic now? WordPress checks `wp-login.php`, which needs PHP + DB), *liveness* (is the process stuck, so a restart helps? We only check that Apache answers, because restarting WordPress doesn't fix a down DB).
- **Helm `lookup` for secrets**: templates generate random passwords. Without `lookup`, every `helm upgrade` would generate *new* ones and lock WordPress out of a DB initialised with the old ones. The helper prefers an explicit value, else the live Secret's value, else a new random one. `helm.sh/resource-policy: keep` stops `helm uninstall` from deleting Secrets whose data volume survives.
- **Helm hooks**: resources annotated `helm.sh/hook` are run at a lifecycle point instead of being part of the release. `post-install,post-upgrade` + `--wait` means the Job runs after MariaDB and WordPress are Ready. `hook-delete-policy: before-hook-creation` keeps the last run (and its logs) until the next one.
- **Why the Job has an initContainer**: `wordpress:cli` has no WordPress core, and the live pod's core isn't on a volume. The initContainer copies core from the same `wordpress` image into an `emptyDir`, and the real `wp-content` PVC is mounted on top. wp-cli then edits the real DB and real plugin directory.
- **Non-root**: MariaDB runs as uid 999, WordPress and the Job as uid 33 (`www-data`). Apache must bind port 80, which normally needs root. The pod sets the namespaced sysctl `net.ipv4.ip_unprivileged_port_start=0`, which Kubernetes treats as "safe" (no cluster config needed).
- **Bug we hit: volume ownership.** First deploy, WordPress crash-looped with `tar: ./wp-content: Cannot change mode ... Operation not permitted`. k3s `local-path` volumes are plain host directories owned by root, and `fsGroup` (which normally makes Kubernetes chown the volume to the pod's group) is *not applied* to that volume type. So the non-root entrypoint couldn't chmod its own mount. Fix: a `volume-permissions` initContainer that runs as root but with every capability dropped except `CHOWN`, and only runs `chown 33:33` on the mount point. It's a values toggle (`volumePermissions.enabled`) because storage that honours `fsGroup` doesn't need it. MariaDB didn't hit this because its entrypoint never chmods the data dir (local-path creates it 0777).
- **WooCommerce API key storage**: WooCommerce stores `HMAC-SHA256(consumer_key, "wc-api")`, never the plain key. The consumer *secret* is stored plain because WooCommerce needs it to verify OAuth 1.0a signatures. We generate both in a Kubernetes Secret and insert the row ourselves (`files/api-key.php`, mirroring `WC_Auth::create_keys()`). So the Job never needs RBAC to write Secrets.

### Likely interview questions
1. **Delete the WordPress pod. Why does nothing get lost?**
   Nothing important lives in the pod. Orders, products and settings are in MariaDB, whose files are on its PVC. Plugins and uploads are on the `wp-content` PVC. WordPress core comes from the image, and the salts come from a Secret, so even login cookies stay valid. The Deployment creates a new pod that mounts the same PVC. Same for `store-mariadb-0`: the StatefulSet recreates it with the same name and reattaches `data-store-mariadb-0`.
2. **Why does running `helm upgrade` twice not break or duplicate anything?**
   Secrets: `lookup` returns the existing values, so passwords never change. Bootstrap: every step checks first (`wp core is-installed`, plugin version, product by SKU, user exists, API key hash already present), and settings are plain "set to X" operations. No pod-restart annotations change either, so pods aren't rolled.
3. **Why generate the API key in Helm instead of letting WooCommerce create one?**
   If WooCommerce generated it, the key would only exist inside WordPress, and the Job would need Kubernetes RBAC to write it into a Secret for the MCP server. Generating it in Helm means the Secret is the source of truth and the Job only needs DB access it already has. The trade-off is that we must match WooCommerce's storage format exactly (HMAC hash, truncated key), which we copy from `WC_Auth::create_keys()`.

## Phase 2: WooCommerce MCP server

### What was built
- `services/woo-mcp`: Python MCP server (official SDK `mcp==2.2.0`, class `MCPServer`) with 6 tools: `get_info`, `list_products`, `create_product`, `list_orders` (incl. `date="today"` in Asia/Kolkata), `get_order`, `update_order_status`. Served over Streamable HTTP at `/mcp` (stateless, JSON responses) by uvicorn, plus `/healthz`.
- `woo_mcp/oauth.py`: a hand-written OAuth 1.0a signer matching WooCommerce's verifier. `woo_mcp/woo_client.py`: thin httpx client (signing, Host header, no redirects, timeouts, clean errors).
- 23 unit tests (REST mocked with `respx`; tools called through a real in-memory MCP client). Run with `make test` inside a Docker build stage.
- `charts/platform` (namespace `platform`): woo-mcp Deployment (non-root, read-only root FS, no service-account token), ClusterIP Service, **no Ingress**, a Secret copied from the store via `lookup`, and a NetworkPolicy.
- Makefile: `test`, `build`, `load-images`, `lint`; `deploy-local` now installs both charts. Image tags are a hash of the source.

### Key concepts
- **MCP in one paragraph**: a JSON-RPC protocol between a *client* (Claude Code, Inspector, later our gateway) and a *server* that offers tools. The client calls `initialize`, then `tools/list` (names + descriptions + JSON Schemas for arguments), then `tools/call`. The tool's result is content the model reads; failures come back as results with `isError: true`, so the model can see and react to them.
- **Streamable HTTP transport**: every MCP message is an HTTP POST to one endpoint (`/mcp`). The server may answer with JSON or upgrade to an SSE stream. We run **stateless** (no `Mcp-Session-Id` kept server-side), so restarts or extra replicas lose nothing. **JSON responses** make it plain request/response.
- **Schemas from type hints**: `Annotated[int, Field(ge=1, le=100)]` becomes `{"type":"integer","minimum":1,"maximum":100}` in `tools/list`. The SDK validates arguments *before* our code runs (our tests prove bad input never reaches the store).
- **DNS-rebinding protection**: the SDK checks the `Host` header. Its default only allows localhost, so in-cluster callers (`woo-mcp.platform.svc...`) would be rejected. We pass the allowed hosts explicitly.
- **OAuth 1.0a (one-legged)**: instead of sending the secret, sign each request: HMAC-SHA256 over method + URL + sorted query params, keyed with the secret. A nonce and timestamp stop replays. WooCommerce requires it over plain HTTP (it refuses Basic auth without TLS). Quirk: WooCommerce signs its *home URL*, so we sign `http://shop.localtest.me/...` while sending to the in-cluster Service with `Host: shop.localtest.me`.
- **Cross-namespace Secrets**: a pod can only use Secrets from its own namespace. Helm `lookup` reads `store/store-woo-api` at deploy time and creates `platform/woo-mcp-store-api`. It fails with a clear message if the store isn't deployed. A checksum annotation restarts woo-mcp if the copied key changes.
- **NetworkPolicy**: once a policy selects a pod, all traffic not explicitly allowed is denied. woo-mcp: ingress only from pods labelled `gateway`; egress only to WordPress pods in `store` on port 80, plus DNS. DNS must be allowed explicitly, or even the store's name won't resolve. k3s *rejects* blocked connections, so they show "connection refused" rather than timing out. `kubectl port-forward` isn't affected: the kubelet connects inside the pod's own network namespace.
- **Image tags from content hashes**: tag = hash of the service's files. Same code → same tag (Helm does nothing); changed code → new tag (Helm rolls the pod). No `latest`, no "did it pick up my change?" confusion.

### Likely interview questions
1. **Why is the MCP server internal-only, and how do you prove it?**
   It holds a store credential that can create products and change orders. The only thing that should use it is the gateway, which adds auth, per-user attribution and audit. So: ClusterIP only, no Ingress, and a NetworkPolicy allowing ingress only from gateway pods. Proof, with controls: a random pod in `platform` is refused, while an identical pod labelled `app.kubernetes.io/name=gateway` gets `ok`. From inside woo-mcp, the store answers 200 while the internet and MariaDB are refused.
2. **Why did you write the OAuth signing yourself instead of using a library?**
   The tricky part isn't the HMAC, it's WooCommerce's quirks: it rebuilds the URL from its home URL, only signs query params, and has a specific encoding and key format. ~30 lines that mirror its PHP verifier are easier to explain and debug than configuring a general library around those quirks. And it's verified: the test's golden signature was accepted by WooCommerce's own `check_oauth_signature()` running in the store pod, and a wrong one was rejected.
3. **What happens when the store is down?**
   woo-mcp stays up and Ready: `/healthz` deliberately doesn't check the store, because restarting woo-mcp can't fix WordPress. Each tool call fails fast (10s timeout) with an MCP tool error, `store unreachable: timed out after 10s`, so the model or user sees a clear reason. The gateway (Phase 4) will keep listing woo-mcp's tools from its cache and report the call error.
